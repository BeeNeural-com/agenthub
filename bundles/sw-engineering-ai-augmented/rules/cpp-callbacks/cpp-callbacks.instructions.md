# C++ Callback Extension Patterns

When a library-owned class must invoke caller-supplied behaviour at an event point, choose one of the four patterns below. `std::function` is **prohibited** in production platform code.

---

## Pattern Selection

```
Need runtime polymorphism (handler swappable at runtime)?
├── No  →  Option 3: Template event_source<Handler>   — zero overhead, compile-time dispatch
└── Yes
    ├── Simplicity is priority (no templates in library)?
    │   └── Yes  →  Option 2: Virtual interface (IEventHandler)
    └── No vtable / strict size budget?
        ├── C++17 available  →  Option 1 C++17: void* + fn ptr, auto NTTP
        └── C++14 only       →  Option 1 C++14: void* + fn ptr, explicit member-fn type
```

`std::function` (Option 0) is permitted only in host-side tooling, unit tests, and prototypes — never in `src/`.

---

## Rules

1. **Never use `std::function` in production `src/` code.** It may heap-allocate and `operator()` is not `noexcept`.
2. **Trampolines are generated by the library** via captureless lambdas in the `setOnEventHandler` template. Handler classes must not define static trampoline methods.
3. **One context pointer per handler object.** Use `setHandlers()` when registering multiple events on the same object.
4. **Follow CP10 naming conventions:** `mOnEventCallback`, `mOnEventContext`, `setOnEventHandler`.

## Self-Check

- [ ] `std::function` not used in any `src/` file
- [ ] Trampoline generated inside the library template — no static trampoline on the handler class
- [ ] Single `setHandlers()` call used when one handler object covers multiple events
- [ ] Pattern chosen matches the decision guide above
- [ ] Member names follow CP10: `m`-prefix `CamelCase`
