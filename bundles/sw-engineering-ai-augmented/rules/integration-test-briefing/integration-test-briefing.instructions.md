# Integration Test Briefing Format

When creating or editing `_briefing.md` files in `doc/<component>/component_integration_tests/`, follow these rules:
- Group briefing items by interaction family (behavioral theme), not by individual element.
- For each group: list the primary sequence/activity diagram ID(s), the element participants, and selected supporting element IDs that materially affect test assertions.
- For each group: describe cross-boundary interactions as stimulus-observable pairs (stimulus on element A, observable effect on element B).
- For each group: list boundary failure modes (what goes wrong at the interface between elements) and edge cases.
- Include an "Integration Scope Decision" section explaining which `arch:` IDs are SWE.5 targets (sequence/activity) versus SWE.4 targets (single-element operations, data structures).

## Purpose

An integration test briefing is a **lightweight domain-content handoff** from the Software Architect to the Integration Tester. It communicates which cross-element interactions need testing, what can go wrong at element boundaries, and which architectural IDs are SWE.5 targets.

A briefing is **not**:
- A process routing document (no 22-field metadata blocks).
- A duplicate of the upstream artifact (no architecture prose).
- A test specification (no TCASE sections, no GTest annotations).
- A per-element breakdown (that leads to single-element tests).

## File Naming and Location

| Briefing type | Producer | Location |
|---|---|---|
| Integration test briefing | Software Architect | `doc/<component>/component_integration_tests/_briefing.md` |

The file name is always `_briefing.md` (leading underscore). One briefing file per component.

## Structure

```markdown
# Integration Test Briefing — <component>

Generated by: Software Architect
Date: <YYYY-MM-DD>
Source artifacts: <path to upstream docs>

## Summary

<1–3 sentences: overall risk assessment, priority guidance>

## Integration Scope Decision

<Explain which arch: IDs are SWE.5 targets (sequence/activity diagrams)
versus SWE.4 targets (single-element operations, data structures).
List all sequence/activity IDs explicitly as a table.>

## Briefing Items

### <Interaction Family Name>

**Primary diagram(s)**: <arch:xxx-seq-yyy, arch:xxx-act-zzz>
**Participants**: <Element A, Element B, ...>
**Supporting IDs**: <arch:xxx-yyy — only those that materially affect assertions>

**Intent**: <what this interaction family achieves — 1 sentence>
**Risk**: <what can go wrong at the boundaries — 1 sentence>

#### Interactions

| # | Stimulus (Source → Target) | Cross-Boundary Observable | Boundary Failure Modes |
|---|---|---|---|
| 1 | <element A action that crosses boundary> | <what element B must exhibit> | <what goes wrong at interface> |
| 2 | ... | ... | ... |

**Edge cases**: <specific boundary conditions — comma-separated list>

### <Next Interaction Family>
...
```

## Rules

### Content Rules

1. **Group by interaction family.** Each `### <Heading>` groups related cross-element behaviors (e.g., "Connection Lifecycle", "Message Exchange"). Do not group by individual element.
2. **Name participants.** Every group must list two or more element participants from the architectural design.
3. **Stimulus-observable pairs.** Each row in the Interactions table describes a stimulus on one element and the expected observable effect on a different element. If both stimulus and observable live in the same element, it belongs in SWE.4, not SWE.5.
4. **Primary diagram IDs.** Reference only `arch:` IDs with `classification: sequence` or `activity`. These are the primary `verifies:` targets for downstream TCASEs.
5. **Supporting IDs.** List element/decision IDs that constrain test assertions (e.g., capacity limits, buffer ownership, transport decisions). Do not list every related element; only those that change what the tester must assert.
6. **Boundary failure modes.** Describe what goes wrong AT the interface between elements, not internal failures. Examples: "message not propagated", "callback fires with invalid handle", "connection accepted beyond capacity".
7. **One sentence per field.** Keep Intent and Risk to one sentence each. Edge cases as a comma-separated list.
8. **Callback contract clarity.** For each interaction involving callbacks, state whether the callback fires on sender-initiated events, receiver-detected events, or both. This prevents wrong assertions from plausible-sounding but incorrect mental models.
9. **No upstream prose duplication.** Do not copy architecture descriptions. Summarize intent in your own words.
10. **No test specification content.** Do not write TCASE sections, expected results, or GTest annotations. The tester writes those.

### Integration Scope Decision Rules

11. **Integration Scope Decision section is mandatory.** Must appear before Briefing Items.
12. **List all primary targets explicitly.** Every `arch:` ID with `classification: sequence` or `classification: activity` must appear in the scope decision and be referenced as a Primary diagram in at least one interaction family group.
13. **Statemachine IDs are secondary.** Include statemachine IDs as Supporting IDs only when their transitions are triggered by cross-element stimuli. Do not list statemachines as Primary diagram IDs.
14. **Element, operation, data, and decision IDs are never Primary.** These appear only as Supporting IDs when they materially constrain assertions.
15. **Explain exclusions.** If an activity diagram is excluded from primary targets (e.g., purely single-element internal flow already covered by sequences), state the rationale.

### Decomposition Authority

16. **Briefing group headings are normative for file decomposition.** Each `### <Heading>` group under `## Briefing Items` prescribes exactly one downstream spec file. The downstream tester must create one spec file per briefing group heading, using the heading as the topic name (lowercased, spaces replaced with underscores, suffixed with `_integration_tests.md`). Do not merge groups into fewer files and do not split a single group across multiple files.
17. **Heading names must be stable identifiers.** Choose heading names as short, plural noun phrases that describe a behavioral phase or interface family. Do not rename headings between briefing regenerations unless the upstream structure changed.

### Staleness Rules

18. **Regenerate when upstream changes.** The briefing must be regenerated whenever the upstream artifacts add, rename, or delete sequence/activity IDs.
19. **The downstream tester validates freshness.** At Triage, the tester compares briefing IDs against current upstream docs and flags discrepancies.
20. **Stale briefings do not block work.** The tester may proceed with a stale briefing after warning the user, but the warning must be given.

## Anti-Patterns

| Anti-pattern | Why it's wrong | Fix |
|---|---|---|
| Grouping briefing items by element | Leads to single-element TCASEs (IR03 failures) | Group by interaction family with cross-boundary stimulus-observable pairs |
| Including same-element stimulus-observable pairs | Not an integration test; belongs in SWE.4 | Remove from interactions table; note as SWE.4 scope in Integration Scope Decision |
| Copying architecture prose into the briefing | Duplicates upstream; drifts silently | Summarize intent; reference the arch: ID |
| Adding metadata fields beyond the defined structure | Process routing, not domain content | Remove; keep only the defined fields |
| Writing expected results or pass/fail criteria | That is a TCASE spec, the tester's job | Remove; describe risk and failure modes only |
| Omitting sequence/activity IDs that exist upstream | Creates false coverage gaps at Triage | List all primary IDs in Integration Scope Decision |
| Listing element/operation IDs as Primary | Misleads tester into single-element tests | Move to Supporting IDs or exclude entirely |
