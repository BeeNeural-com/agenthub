# Qualification Test Briefing Format

When creating or editing `_briefing.md` files in `doc/<component>/component_qualification_tests/`, follow these rules.

## Purpose

A qualification test briefing is a **lightweight domain-content handoff** from the Requirements Engineer to the Qualification Tester. It communicates intent, risk, and suggested test approach for each testable requirement ID.

A briefing is **not**:
- A process routing document (no 22-field metadata blocks).
- A duplicate of the upstream artifact (no requirement text).
- A test specification (no TCASE sections, no GTest annotations).

## File Naming and Location

| Briefing type | Producer | Location |
|---|---|---|
| Qualification test briefing | Requirements Engineer | `doc/<component>/component_qualification_tests/_briefing.md` |

The file name is always `_briefing.md` (leading underscore). One briefing file per component.

## Structure

```markdown
# Qualification Test Briefing — <component>

Generated by: Requirements Engineer
Date: <YYYY-MM-DD>
Source artifacts: <path to upstream docs>

## Summary

<1–3 sentences: what changed, overall risk assessment, priority guidance>

## Briefing Items

### <Heading>

#### <req: ID>

- **Intent**: <what this requirement is trying to achieve — 1 sentence>
- **Risk**: <what can go wrong; why this needs testing — 1 sentence>
- **Test approach**: <suggested technique or scenario class — 1 sentence>
- **Edge cases**: <specific boundary conditions, error paths, or concurrency concerns — comma-separated list>

#### <next req: ID>
...
```

## Rules

### Content Rules

1. **3–4 bullets per ID.** Intent, Risk, Test approach, and Edge cases. Do not add more fields.
2. **One sentence per bullet.** Keep each bullet to a single clear sentence or a comma-separated list (for edge cases).
3. **No upstream prose duplication.** Do not copy requirement text. Summarize intent in your own words.
4. **No test specification content.** Do not write TCASE sections, expected results, or GTest annotations. The tester writes those.
5. **Use upstream vocabulary.** Terms must come from the upstream requirements and the project glossary.

### ID Coverage Rules

6. **List all testable IDs.** All `req:` IDs where `:verification_method:` is `dynamic_test` or `static_test`.
7. **Do not invent IDs.** Every ID in the briefing must exist in the current requirements.
8. **Group by topic file** if the upstream artifacts are organized into topic files. Use the topic file name as a section header above the ID groups.

### Decomposition Authority

9. **Briefing group headings are normative for file decomposition.** Each `### <Heading>` group under `## Briefing Items` prescribes exactly one downstream spec file. The downstream tester must create one spec file per briefing group heading, using the heading as the topic name (lowercased, spaces replaced with underscores, suffixed with `_qualification_tests.md`). Do not merge groups into fewer files and do not split a single group across multiple files.
10. **Heading names must be stable identifiers.** Choose heading names as short, plural noun phrases that describe a behavioral phase or interface family. Do not rename headings between briefing regenerations unless the upstream structure changed.

### Staleness Rules

11. **Regenerate when upstream changes.** The briefing must be regenerated whenever the upstream artifacts add, rename, or delete IDs that are in scope.
12. **The downstream tester validates freshness.** At Triage, the tester compares briefing IDs against current upstream docs and flags discrepancies.
13. **Stale briefings do not block work.** The tester may proceed with a stale briefing after warning the user, but the warning must be given.

## Anti-Patterns

| Anti-pattern | Why it's wrong | Fix |
|---|---|---|
| Copying full requirement `:verification_criteria:` into the briefing | Duplicates upstream; drifts silently | Summarize intent; link to the req: ID |
| Adding `priority:`, `category:`, `owner:` metadata fields | Process routing, not domain content | Remove; keep only the 4 bullets |
| Writing expected results or pass/fail criteria | That is a TCASE spec, the tester's job | Remove; describe risk and approach only |
| Omitting IDs that exist upstream | Creates false coverage gaps at Triage | List all testable IDs |
